# Exploration: Refactor `/wf-refresh` to builder-driven migration

**Change name**: `refactor-wf-refresh-builder-driven`

## Current state analysis

### What exists today

1. **`/wf-refresh` current implementation** (`templates/commands/wf-refresh/_base.md`):
   - Layer 1: Project content drift detection (reverse engineering)
   - Layer 2: Template drift (manifest-driven regeneration)
   - Layer 3: Optional features
   - Uses `WIZARD_MANIFEST.json` (static, incomplete)
   - Has its own `render_template()` bash function (lines 289-369)
   - Cannot handle nested placeholders, per-IDE skills, or complex variants

2. **Builder architecture** (`wf-init/lib/builder.md`, subagent-*.md):
   - Deterministic B1-B9 phases
   - Writes to `.wizard-staging/` on disk
   - Handles all template types, per-IDE variants, skills, protocols
   - Single source of truth for artifact generation
   - Already proven in `/wf-init`

3. **State contract** (`.wizard-state.json`):
   - `schema_version: 2`
   - `build_plan` exists but incomplete (no `generated_files`, no `managed_paths`)
   - No tracking of "files wizard owns" for deletion detection

4. **Manifest** (`WIZARD_MANIFEST.json`):
   - Auto-generated by release-please.yml
   - Tracks template changes but not full file inventory
   - Only consumed by `/wf-refresh` and `/wf-cleanup`
   - Dead code once refresh is builder-driven

### Problems with current approach

- **Duplicate rendering logic**: `/wf-refresh` has its own template engine that diverges from Builder
- **Incomplete file tracking**: no way to detect deprecated files to delete
- **Risk of deleting user skills**: broad `*` patterns in cleanup logic
- **Custom AGENTS.md rules not preserved**: no robust marker support
- **State/schema drift**: new features not migrated automatically
- **Per-IDE skills out of sync**: Phase 3.5 only checks universal `.agents/skills/`

## Proposed solution (Option A: Full builder + hash diff)

### Architecture

1. **Global command refresh** (Phase R-1):
   - Compare local `wf-init`, `wf-refresh`, `wf-cleanup` versions with remote `VERSION`
   - Propose/run `install.sh` if outdated

2. **Project discovery** (Phase R1):
   - Re-run `subagent-discovery.md` commands
   - Update `.wizard-state.json` (`discovery.*`, `answers.*`)
   - Detect drift in project structure

3. **State migration** (Phase R2):
   - Run `migrations.md` to bring old schema to current
   - Ask about new optional features
   - Never auto-enable features without approval

4. **Builder re-run** (Phase R3):
   - Clean `.wizard-staging/`
   - Run Builder-Core + Builder-Heavy (B1-B9)
   - Generate everything into staging

5. **Hash-based diff** (Phase R4):
   - Compare SHA256 of each staging file vs project file
   - Classify: `add`, `update`, `delete`, `unchanged`
   - Only `unchanged` files are skipped (not copied)

6. **Review gate** (Phase R5):
   - Show grouped diff
   - Require explicit approval for deletions
   - Never auto-delete user skills or custom content

7. **Apply and close** (Phase R6):
   - Copy approved adds/updates
   - Delete approved removals
   - Update `.wizard-state.json` and `.wizard-managed-files.json`
   - Commit with conventional message
   - Clean staging

### Key design decisions

| Decision | Rationale |
|----------|-----------|
| Reuse Builder (B1-B9) | Single source of truth; scales to new releases automatically |
| Hash-based comparison | Avoids re-writing identical files; detects real changes |
| `.wizard-managed-files.json` | Tracks what wizard owns; enables safe deletion detection |
| Explicit deletion approval | Never auto-delete; user controls what goes away |
| Preserve `<!-- WF: DO NOT REGENERATE -->` | Respects custom AGENTS.md rules |
| Deprecate `WIZARD_MANIFEST.json` | Dead code once refresh is builder-driven |

## Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| Builder bug affects both `/wf-init` and `/wf-refresh` | Single source of truth is correct tradeoff; add focused tests |
| Deleting user edits | Only delete files in old `managed_paths` with matching SHA256; warn otherwise |
| Losing custom AGENTS.md rules | Use explicit markers; show full diff if no markers |
| Schema migrations fail on old projects | Support migrations from any version with valid `.wizard-state.json` |
| Removing manifest breaks release-please | Remove only `update-manifest` job, not release creation; keep files as historical artifacts |

## Comparison with alternatives

### Option B: Incremental builder (only regenerate changed files)
- **Pro**: Saves tokens by not regenerating unchanged files
- **Con**: Requires dependency graph (template → output); complex to maintain
- **Decision**: Defer to Opción C in future iteration

### Option C: Pre-flight with manifest
- **Pro**: Skip builder entirely if nothing changed
- **Con**: Still need manifest generator; adds complexity
- **Decision**: Defer to future iteration after Opción A is stable
