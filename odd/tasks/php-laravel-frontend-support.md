## Specs

S1. "quiero ahora dar soporte a PHP/laravel, y tengo un proyecto que dentro de laravel tambien tiene react" (L1). Laravel with a React/Vue frontend in the same root must be detected and configured; today R1 picks Node when both `composer.json` and `package.json` exist and Laravel is lost.
S2. Model (L5): one primary stack plus a `frontend` field (`react` | `vue` | `none`), not a list of stacks. "como tu lo sugieres" = primary + frontend. `discovery.stack.stack_key` stays `php-laravel`.
S3. `frontend` is derived from React/Vue (or another UI framework) in `package.json` dependencies, never from the mere presence of `package.json` (the Laravel skeleton ships one with Vite and axios and no UI). A pure Laravel backend gets `frontend: none` and only the PHP profile. Livewire/Blade without a JS framework is `none`.
S4. PHP testing profile for PHPUnit/Pest: a project that already has a runner keeps it (`runner_existing`); otherwise the wizard installs and configures one. The profile schema must stop assuming npm (install and run commands for composer).
S5. Frontend testing reuses the existing JS profiles (`react`, `next`, `vue`, `angular`, `generic`); the bundler (Vite, Mix, webpack) does not select the profile.
S6. "estándar por defecto, y para lo no estándar detectar y confirmar en vez de adivinar" (L10): a standard Laravel + Vite + `resources/js` project asks nothing. Non-standard layouts (JS in `resources/assets/js`, Mix/webpack/Babel) are detected from facts of the project (JS source dir, existing runner, `package.json` and `composer.json` scripts); when detection is ambiguous the wizard asks once and stores the answer in the state as an override (JS root, test commands). What the wizard does not understand falls to `generic`, and the generated `AGENTS.md` says so instead of inventing commands.
S7. Commands and CI: `STACK_OVERRIDES` gets a `php` row and composer scripts are read like `detect_package_scripts` reads npm scripts; a PHP quality guard variant (composer install, pint, phpstan if present, phpunit) and a JS job when `frontend` is not `none`.
S8. Router, satellites, `templates/commands/*` base and the state machinery stay agnostic and unchanged in behavior for every existing stack; Node-only projects must produce identical output.
S9. `AI_DEV_WORKFLOW.md` and the README Supported Frameworks are synced before each commit that touches the topics in `AGENTS.md`.

Acceptance (two fixtures in `mktemp -d`, never inside the repo): (a) a fresh standard Laravel + React/Vite skeleton, (b) a copy of `<path of the reference project>` without `.env`, `vendor/` or `node_modules/` as the non-standard case. Expect (b): `php-laravel`, `frontend=react`, runner `phpunit` kept, JS root `resources/assets/js`. Differential check: Node-only fixtures (vite-react, next, vue, express, nest, angular) give the same output as the base commit.

Assumption (not verified): Vitest + `@vitejs/plugin-react` may need extra config for the reference project's Babel decorators and `create-react-class`; to be tested on the fixture, fallback is a different Vitest config template.
